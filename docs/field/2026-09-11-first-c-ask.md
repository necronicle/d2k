# Первый вопрос настоящей коробке из C — 11.09.2026

Живой прогон, не стенд: z2k выключен, d2k работает, трафик идёт через него.
Цель — `www.instagram.com` (157.240.253.174:443), утилита `d2kask` (core/d2kask.c)
на роутере, Go-контроллер на время прогона снят, чтобы не ставить конкурирующие
планы.

## Что получилось

Ловушка формы сработала с первого раза. Датапат поймал НАСТОЯЩЕЕ приветствие
живого клиента и отдал его по управляющему сокету:

    снимок триггера: --arm-wait-ms (имя=www.instagram.com, потолок=45000 мс), 327 байт
      SNI в снимке: www.instagram.com
      вид приветствия: MODERN

То есть связка `D2K_CMD_ARM_SHAPE` → `D2K_EV_SHAPE` → `d2k_hello_sni` работает
на боевом датапате, а не только против `ctlprobe`.

## Что не получилось

Все пять вопросов остались «не измерено»: два не задавались вовсе (нет
control-приветствия — без него не собрать фальшивку для «счёта дубликатов» и
«разбора протокола»), три задались и не прошли.

И вот здесь вывод оказался бесполезен. На каждый заданный вопрос печаталось:

      план: неизвестно снаружи (d2k_props_ask не отдаёт трассировку одного зонда)
      обмен: неизвестно снаружи

«Не прошёл» — это по меньшей мере пять разных событий: план не собрался, команда
не ушла, подтверждение не пришло, датапат отверг план, обращение не состоялось,
обмена не было, обмен был без прикладных данных. Первые четыре — про НАС, два
последних — про коробку. Смешивать их в одну строку значит не уметь отличить
свой дефект от наблюдения, а это ровно та ошибка, из-за которой
`docs/field/2026-09-05-active-probe.md` пришлось переписывать.

## Что сделано по итогу

1. `d2k_props_ask_traced` (core/compose.c) — та же функция, плюс трасса пяти
   вопросов: чем кончился каждый шаг, длина плана, код отказа датапата, местный
   порт обращения, набор встреченных типов TLS-записей, число байт обмена.
   `d2k_props_ask` осталась как есть и зовёт её с `NULL`.
2. `d2kask` печатает эту трассу вместо «неизвестно снаружи».
3. `d2k_link_del_name` (core/link.c) + снятие плана по итогу ПОЛНОГО промаха:
   до этого на боевом датапате оставался стоять план, про который это же
   измерение только что сказало «не работает». Прошедший план по-прежнему
   остаётся — он и есть найденная стратегия.
4. `ctlprobe` больше не умирает от SIGPIPE, когда клиент отваливается между его
   записями (то же `signal(SIGPIPE, SIG_IGN)`, что в `d2kd.c` стоит с самого
   начала). Всплыло ровно на DEL_NAME: утилита шлёт команду и почти сразу
   закрывает сокет. Боевой датапат этим не болел — только тестовый сервер.
5. `--save-trigger` / `--save-control` — снятые приветствия пишутся в тот же
   формат, который читают `--hello-hex` / `--control-hex`. Армирование стоит окна
   ожидания и ручного захода на цель; платить эту цену на каждый повтор одного
   и того же измерения незачем.
6. `core/Makefile`: `d2kask-aarch64` теперь зависит от `hello_profiles.inc` —
   на чистом дереве цель падала с `fatal error: 'hello_profiles.inc' file not found`.

## Второй прогон — трасса сразу назвала виновного

Тот же роутер, то же время, control-снимок снят с `www.microsoft.com` (тоже
через ловушку формы, 327 байт, MODERN). Все ПЯТЬ вопросов задались, и все пять
дали одно и то же:

    план: 58 байт, датапат принял
    обмен: обращение с местного порта 54566, события обмена не пришло
    причина остановки: своего обмена не было в срок

Пять разных манипуляций, пять принятых планов, пять состоявшихся обращений — и
ноль событий обмена. Не «мало», а РОВНО ноль, включая событие первого уровня
(оно приходит и на один ServerHello). Такая ровность — не поведение коробки.

Причина нашлась в паре строк на разных концах дерева. `props_ask_contact`
(core/compose.c) закрывала сокет сразу после посылки приветствия:

    /* Локальный recv не читается вовсе — судит только датапат */
    close(fd);

а датапат (datapath/session.c) по закрытию удаляет ячейку потока:

    if (rst || fin) { ... d2k_track_remove(s->flows, &key); ... }

FIN уходит через микросекунды после приветствия. Ответ сервера приходит через
RTT — то есть в ячейку, которой уже нет; новая заводится с `saw_hello == 0`, а
`D2K_JRN_EXCHANGE` журналируется ТОЛЬКО при `saw_hello`. Событие обмена не могло
прийти НИКОГДА — ни для одного вопроса, ни на какой коробке.

«Не читать из сокета» и «закрыть сокет» — разные вещи; дисциплина «судит только
датапат» требовала первого, а код делал второе. Теперь `props_ask_contact`
возвращает открытый сокет, а закрывает его вызывающий — после ожидания обмена.

Тест, который поймал бы это: стенд `test_compose` держит свою половину
соединения открытой и смотрит, не закрыл ли зонд свою ДО события обмена
(`peer_closed`). Проверено снятием правки — падают все пять случаев с
поддельным концом связи.

## Третий прогон — второй дефект того же рода

С исправленным зондом и теми же снятыми снимками (`--hello-hex` / `--control-hex`,
живой трафик больше не нужен) картина изменилась:

    [1/5] перекрытие слева
      обмен: с местного порта 54600, 1380 байт, первая запись типа 22, встречены типы: 22 рукопожатие
      причина остановки: обмен был, но без прикладных данных (§8)

    [3/5] порядок сегментов
      обмен: с местного порта 54612, 1380 байт, первая запись типа 22, встречены типы: 22 рукопожатие

    [2/5], [4/5], [5/5] — события обмена не пришло

То есть по двум вопросам манипуляция ДОШЛА до сервера и сервер ответил. Три
оставшихся — те, что строят фальшивку с битой контрольной суммой, — обмена не
дали вовсе.

Но «1380 байт, только тип 22» — это опять не про коробку. Датапат сообщает об
обмене ДВАЖДЫ (datapath/session.c, комментарий у `D2K_JRN_EXCHANGE`):

    Сообщаем дважды: когда обмен вообще пошёл и когда в нём появились
    ПРИКЛАДНЫЕ данные. Это разные уровни доказательства (§4.2), и второй
    наступает позже первого — сообщить только о первом значит навсегда
    оставить контроллер на уровне 2.

`d2k_props_ask` брала ПЕРВОЕ событие и по нему судила — ровно то, от чего
предостерегает этот комментарий. 1380 байт — это один пакет: первый ответный
пакет сервера. Сервер TLS 1.3 досылает весь второй полёт (записи типа 23) сам,
без единого действия клиента (RFC 8446 §5.1), но опрос к тому моменту уже
объявил промах.

Теперь опрос ждёт события с прикладными данными в пределах ТОГО ЖЕ бюджета
(продлевать его каждым пришедшим событием значило бы отменить потолок вовсе).
Тест B6: стенд шлёт два события подряд — сперва без прикладных данных, через
150 мс с ними; проверено снятием правки, падает.

## Что осталось открытым

Прогон с обеими правками. Три вопроса с фальшивкой по битой сумме не дали обмена
совсем — пока неизвестно, это коробка, путь или наша фальшивка; смотреть после
того, как первые два вопроса начнут отвечать. Отдельно: потолок
`D2K_PROPS_ASK_WAIT_MS` (5000мс) так и не измерен для этого применения — теперь
он к тому же держит соединение открытым ровно столько же.

# Первый живой прогон d2kc — 11.09.2026, вечер

Контроллер на C (`core/d2kc.c` + `core/sched.c`) заменил Go-процесс на боевом
роутере. Go остановлен, z2k остановлен, обход делает только d2k.

## Цепочка прошла целиком

    17:33:44 по www.speedtest.net (TCP) начинаю поиск: 104.17.148.22:443, приветствие 1540 байт, снимок заказан
    17:33:44 по www.speedtest.net поймана форма приветствия: 327 байт
    17:34:15 по www.speedtest.net вердикт: решает содержимое (разрез не помог,
             но контроль другим именем прошёл (3/3) — решает содержимое, поток пересобирается), кандидатов 1
    17:34:15 по www.speedtest.net поставил кандидата 1 из 1, жду обмена

Датапат заподозрил цель → планировщик завёл задачу → ловушка формы сняла
НАСТОЯЩЕЕ приветствие клиента → дерево вердиктов отработало на живой линии →
`d2k_compose` собрал кандидата → перевод текста в байты провода → датапат план
принял и применил. Всё это на C, без единой строки Go.

## Три дефекта, которые нашёл только живой прогон

**1. Кандидат залипал навсегда.** Применился шесть раз без обмена — и поиск
стоял. Предела молчаливых применений у планировщика не было; у Go-стороны он
есть (`maxSilentTries = 2`) с обоснованием, которое перенесено дословно.

**2. Каталог лежал мёртвым грузом.** `d2kc` читал 14 коробок и 353 привязки — и
не ставил из них ничего. Go делает это при каждом запуске (`Sync`), и его
комментарий объясняет почему: «датапат состояния между запусками не хранит,
знание живёт в каталоге». После правки:

    17:57:31 каталог: поставлено планов по подтверждённым привязкам: 353

и свежий, только что перезапущенный датапат сразу отдаёт instagram (200),
youtube (200), facebook (200), dtf.ru (200) — ни одного поиска не понадобилось.

**3. `proto` плана — не транспорт.** Узнавание коробки отбирало её планы по
`strcmp(plan.proto, "tcp")`. В живом каталоге роутера у ВСЕХ 353 планов
`proto == "tls"`: это протокол уровня приложения, а не транспорт. Сравнение с
транспортом отбрасывало бы каждый настоящий план узнанной коробки — узнавание
работало бы только в тесте, где план заводил сам планировщик.

## Честное сравнение с Go

`rutracker.org` под d2kc не открывался. Под Go-контроллером на той же линии в
ту же минуту — тоже: два таймаута по 22 секунды, открылся с третьего раза за
13 секунд (свежий поиск). То есть это поведение ЛИНИИ, а не проигрыш C-стороны.

## Ловушка, которую стоит помнить

Первый прогон d2kc был поставлен на линии, где z2k работал одновременно с d2k.
z2k при старте перестраивает mangle и сносит правила d2k: цепочки `D2K_IN`/
`D2K_OUT` остаются подцепленными, а NFQUEUE-правил на очередь 2000 внутри них
больше нет. Датапат при этом не получает НИ ОДНОГО пакета, а обход целиком
делает z2k — и любое измерение d2k в этот момент меряет пустоту. Проверять
надо не процесс, а правило: `iptables -t mangle -S | grep "queue-num 2000"`.
