# Промах conntrack: один ответ «нет записи» ещё не ответ

17.09.2026. Продолжение [передачи 17.09](2026-09-17-hold-and-cancel.md), где
дефект был найден, но не разобран.

## Что было видно

Стенд транзита зелёный, но не стабильно: 3/3, 3/3, 2/3 и один прогон целиком
красный. В журнале датапата — отказ:

```
приветствие tranzit.example
план не применён: поток не ведётся conntrack — посылки уйдут мимо NAT
```

Отказ ПРАВИЛЬНЫЙ по смыслу: без записи conntrack посылки плана уйдут с
локальным адресом мимо NAT и умрут у провайдера (13.09,
`2026-09-13-transit-vs-local.md`). Вопрос был в другом — почему записи нет,
если приветствие TCP третий пакет потока и запись давно подтверждена.

## Как воспроизвели

Три обращения клиента ловят такое раз в несколько прогонов — на них нельзя
отличить «починили» от «не повезло». Стенду добавлены два ключа:

* `D2K_LAB_CLIENT_TRIES` — сколько раз спрашивать клиентом (умолчание 3);
* `D2K_LAB_CLIENT_PAR` — сколько клиентов разом (умолчание 1).

Один клиент по очереди — это не роутер: там разом ходят телефон, телевизор и
ноутбук, и таблица соединений всё это время меняется под руками. На тридцати
обращениях дефект стал ловиться.

Заодно журналы прогона теперь переживают контейнер (`keep_logs` в драйвере,
каталог задаётся `D2K_LAB_OUT`): `--rm` уносил их вместе с контейнером, а
разбирать приходится именно их.

## Что показал замер

Временная диагностика в датапате: при промахе повторить запрос сразу же, без
паузы, и записать исход.

```
ИЩЕМ proto=6 src=10.50.0.1 sport=34243 dst=10.50.0.2 dport=443
ПОВТОР СРАЗУ ЖЕ: rc=0
```

**Запись существует.** Первый запрос её не увидел, повторный через микросекунды
— увидел. Чтение `/proc/net/nf_conntrack` не атомарно: таблица меняется, пока
мы её читаем.

Снимок таблицы, снятый в момент промаха, это подтвердил: искомая строка в нём
есть, свежая (`packets=3`, полный остаток жизни).

## Почему цена несоразмерна редкости

Порт из замера — **34243** — это порт СОБСТВЕННОГО ЗОНДА подтверждения. Цепочка
из того же прогона:

```
06:40:49 приём «disorder» НАЙДЕН замером — ставлю его первым кандидатом
06:40:49 поставил план 1 из 1 (порт зонда 34243) — испытываю его своим зондом
06:40:54 план 1: зонд не дошёл до приложения — беру следующего кандидата
06:40:54 выведенные планы исчерпаны — цель отдыхает
         прошло 0 из 30
```

Один промах на потоке зонда → план к зонду не применился → зонд не дошёл →
единственный найденный кандидат объявлен негодным → цель осталась без обхода
ЦЕЛИКОМ. Не «один клиент из тридцати», а все тридцать.

Это тот же класс, что седьмая находка лаборатории 13.09: доказательство
настоящее, но не про тот путь. Только здесь наоборот — путь тот, а
доказательства нет из-за чужой гонки.

## Что сделано

Промах перепроверяется: три попытки подряд, без пауз между ними.

* **Три, а не одна** — одна это и есть прежнее поведение.
* **Три, а не десять** — каждая попытка стоит чтения таблицы в сотни строк на
  пакетном пути, и платить эту цену придётся КАЖДЫЙ раз, когда записи
  действительно нет: ускоритель, ведущий поток мимо conntrack, на роутере
  обычное дело. Замеренный случай лечился первым же повтором.
* **Без пауз** — очередь NFQUEUE обрабатывается одним потоком, и сон здесь
  тормозит весь трафик, а не только этот пакет.

Настоящее отсутствие записи по-прежнему отвергает план: перепроверка лечит
гонку, а не отменяет проверку.

В итог датапата добавлено число «спасла перепроверка»: по нему в поле видно,
насколько часто чтение промахивается на живой нагрузке и не пора ли
спрашивать ядро иначе, чем через procfs.

## Чем проверено

`d2k_nat_hook` — точка подмены справки о трансляции, по образцу `d2k_mark_hook`
и по той же причине: состояние ядра машины, где идёт тест, не должно решать
вердикт. Два теста в `test_session`:

* первый ответ «нет», следом «есть» → план ОБЯЗАН примениться;
* ответ всегда «нет» → план обязан быть отвергнут, и перепроверок не больше
  восьми.

Оба падают без правки (проверено снятием: с одной попыткой вместо трёх).
`make -C datapath check`, `san` и `cross` зелёные.

**Живой датапат проверен отдельно, инсценировкой.** Ждать редкой гонки на
стенде оказалось бесполезно: четыре прогона по сорок клиентов (по десять
разом) прошли 40/40, и перепроверка не понадобилась ни разу — гонка просто не
выпала. Поэтому промах инсценирован: временной правкой ПЕРВЫЙ ответ всегда
объявлялся «нет записи».

```
прошло 20 из 20 (по 10 разом)
поток ведётся conntrack: да 21, нет 0, таблицы нет 0, спасла перепроверка 21
```

Перепроверка спасла все двадцать одну справку, и клиент прошёл везде. Тот же
прогон без инсценировки: 20/20, «спасла перепроверка 0» — на исправной машине
лишней работы не делается.

Это доказывает, что механизм работает на живом пакетном пути, а не только в
тесте с подменённым крючком. Чего оно НЕ доказывает: что именно исходная
редкая гонка теперь лечится. Прямого «было красно → стало зелено» на стенде
нет — дефект слишком редок, чтобы поймать его по требованию.

## Чего этот разбор НЕ закрывает

Точный механизм промаха внутри ядра не установлен — известно лишь, что запись
есть, а чтение её не видит. Радикальное лечение — спрашивать conntrack через
netlink точечным запросом вместо чтения всей таблицы (`datapath/nl.c` уже
умеет netlink). Это отдельная работа; пока она не сделана, счётчик
перепроверок покажет, нужна ли она.
