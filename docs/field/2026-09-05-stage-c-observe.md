# Этап C: наблюдение транзитного трафика на устройстве

**Дата:** 2026-09-05
**Устройство:** Keenetic, aarch64, ядро 4.9-ndm-5, MediaTek MT7622 с аппаратным PPE, WAN `ppp0`.
**Линия:** z2k остановлен (`ENABLED=0` в `/opt/zapret2/config`), правил NFQUEUE ни в одной таблице нет, `/proc/net/netfilter/nfnetlink_queue` пуст. Проверено перед прогоном.
**Клиент:** один хост в LAN, 192.168.1.67.
**Служба:** `d2kd`, статическая сборка aarch64-musl, режим `observe`.
**Воспроизведение:** `D2K_ROUTER=… D2K_SSH_PASS=… sh scripts/field-observe.sh`

## Критерий, заданный до прогона

Этап C считается пройденным по backend, если на устройстве видны реальные
транзитные соединения тестового клиента, протокол узнаётся, и трафик не
повреждается. Числа CPU и пропускной способности здесь не пороги: они
измерены на этапе 0 и от режима наблюдения не зависят.

## Правила

```
mangle POSTROUTING -p tcp --dport 443 -m connskip --connskip 1000000 -j PPE
mangle POSTROUTING -p tcp --dport 443 -m connbytes --connbytes 0:8 \
       --connbytes-dir original --connbytes-mode packets \
       -j NFQUEUE --queue-num 537 --queue-bypass
```

Первое снимает аппаратный офлоад с направления клиент→сервер, второе отдаёт в
очередь первые восемь пакетов каждого соединения. Оба помечены комментарием с
жетоном запуска и снимаются по нему.

Обратное направление намеренно НЕ де-оффлоадится: этап 0 показал, что полная
видимость обеих сторон стоит 66 % процессора и режет скорость до 73–80 Мбит/с.
Для узнавания ClientHello обратное направление не нужно.

## Прогон 3: цена узкого окна и обнаружение подозрений

Настройка: окно `connbytes 0:8` в ОБА направления, аппаратный офлоад НЕ
снимается. Нагрузка: три параллельных загрузки `ls-lR.gz` с
`mirror.yandex.ru` по 25 с плюс семь проб к разным целям. 90 секунд.

```
пакетов 317, байт 75401, пропущено 317, снято 0
потоков 32 из 2048, отказов таблицы 0
узнано приветствий 13, из них с именем 13, подозрений 8
потеряно ядром 0, ошибок вердикта 0
процессор 0 мс за 90 с, RSS 628 КиБ
```

Процессорное время НИЖЕ разрешения счётчика: меньше одного тика (10 мс) за 90
секунд. Индексы полей `/proc/self/stat` сверены на устройстве: для ndm они
дают 11 854 с процессора при uptime 715 643 с, то есть 1,66 % в среднем —
правдоподобно для главного демона Keenetic.

Пакеты загрузок в очередь не попали вовсе: они за пределом окна. Это и есть
смысл узкого окна — см. `docs/decisions/0003-visibility-budget.md`.

Два РАЗНЫХ наблюдаемых поведения на одной линии: сброс в ответ на приветствие
и тишина с повтором приветствия. Это ровно тот различающий признак, ради
которого §3.5 заводит короткое распознавание моделей коробок. Из него НЕ
следует, что коробок две: §2.4 запрещает такой вывод, и разные цели могли
попасть под разные механизмы одной цепочки.

Подозрения появились и на трафике других хостов LAN (192.168.1.90,
192.168.1.136) без всякого участия измерения — линия наблюдается целиком.

## Что это доказывает и чего не доказывает

Доказано:

- транзитные соединения LAN-клиента доходят до службы и узнаются;
- имя цели извлекается из настоящего ClientHello, а не из подготовленного;
- в режиме наблюдения ни один пакет не снят и не изменён;
- очередь не теряла сообщений и не отказывала на этой нагрузке.

**Не доказано** и требует отдельных прогонов:

- поведение под настоящим числом пакетов: 317 за 90 с — это по-прежнему
  тишина. Узкое окно её и обеспечивает, но на очередь с тысячами новых
  соединений в секунду служба не смотрела;
- режим `apply`: ни один собственный пакет ещё не уходил на провод с этого
  устройства, и корректность адресов после NAT не проверена;
- поздние обрывы соединения: окно `connbytes 0:8` их не покрывает по
  построению, и §5.2 прямо требует проектировать их обнаружение отдельно;
- IPv6: правило и привязка очереди только для `AF_INET`;
- поведение при смерти службы под трафиком (`--queue-bypass` и fail-open
  выставлены, но не проверены выстрелом).

## Найденные дефекты

1. **Узнавание протокола стояло после проверки плана.** Первый прогон дал 145
   пакетов с единственной причиной пропуска «плана нет»: о протоколе не
   узналось ничего. Наблюдение не имеет права зависеть от наличия воздействия.
   Разбор переставлен вперёд и ограничен первыми восемью пакетами потока —
   предел свой, а не унаследованный от правила firewall.
2. **Сводка врала о пределе таблицы:** вторым числом печаталась длина очереди
   отправки, и строка читалась как «23 потока из 0».
3. **Правило ставилось с комментарием, а снималось без него** — и оставалось
   висеть после неудачного запуска. Снятие теперь идёт по жетону: читаем
   `iptables -S`, меняем `-A` на `-D`.
4. `nohup` на BusyBox нет; служба уходит в фон через `start-stop-daemon` и сама
   открывает свой журнал по `--log`.
5. У dropbear на Keenetic нет `sftp-server`, `scp` закрывает соединение.
   Доставка идёт потоком через `ssh`, размер сверяется на той стороне.

## Ограничение, объявленное а не обойдённое

Сырой сокет с `IP_HDRINCL` не распоряжается идентификатором IP: по `raw(7)`
ядро подставляет свой, когда в заголовке ноль. Порча `D2K_POISON_IPID_ZERO`
этим способом отправки неисполнима. Служба ОТКАЗЫВАЕТСЯ активировать такой
план вместо того, чтобы отправить «почти то же самое»: §2.5 запрещает молча
приближать операцию другой. Снять ограничение может только переход на
`AF_PACKET` с ручной сборкой канального заголовка — отдельная работа с
отдельной проверкой на устройстве.

Сумма TCP этим не задета: её считаем мы, и ядро её не трогает. Порча
`D2K_POISON_BADSUM` доезжает до провода как задумано — проверено сборкой, не
на устройстве.

## Уборка

После каждого прогона: правила сняты по жетону (проверено `iptables -S`),
служба погашена, `/tmp` роутера очищен. Ничего не писалось на флеш-накопитель.
