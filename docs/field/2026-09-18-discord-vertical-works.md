# 18.09.2026. Вертикаль пробивает Discord сама

**Итог:** контроллер сам измерил, сам вывел приём, сам поставил план, сам
подтвердил его своим зондом, и обычный клиент через роутер пошёл.

```
12:28:42 приём «seqovl-1» НАЙДЕН замером — ставлю его первым кандидатом
12:28:45 ПОДТВЕРЖДЕНО собственным зондом: plan-02dfb78d, приложение ответило 200
12:28:48 каталог: поставлено планов по подтверждённым привязкам: 1
попытка 3: 200 appconnect=0.130   попытка 4: 200   попытка 5: 200   попытка 6: 200
план подготовлен 5, ДОИСПОЛНЕН 5, выпущено 5, сырым сокетом отправлено 5, ошибок 0
```

До этого захода вертикаль не доезжала до провода НИ РАЗУ, хотя замер приём
находил. Причин оказалось четыре, и каждая закрыта отдельно.

## 1. Новый SYN не сбрасывал состояние потока

Запись потока живёт дольше соединения: эфемерный порт возвращается в оборот, и
следующее соединение попадает в ту же ячейку. Начало потока бралось только при
ПЕРВОМ SYN (`if (!fl->saw_syn)`), а пометки «приветствие было» и «попытку
удержания делали» не снимались никогда. Новое соединение получало чужой ISN
(якорь сборки указывал в никуда) и закрытую навсегда дорогу к удержанию.

Чинится `d2k_track_new_connection`: SYN без ACK — граница соединений, и всё,
что принадлежит соединению, обнуляется целиком (сохраняются ключ, времена
ячейки, счётчики наблюдения и учёт незавершённых посылок).

## 2. Удержание головы само себе перекрывало кислород

Составное приветствие удерживалось до сборки: голова лежит в очереди без
вердикта, ждём остаток. **Остатка не бывает.** Замер назвал это прямо — новые
счётчики удержания за три прогона подряд:

```
начато=2 собрано=0 отпущено=2 таймаутов=2 (пакетов в них=2)
по смене плана=0 по сбросу=0 добавлено к голове=0 несовместимых=0 с другой стороны=0
```

`добавлено к голове=0` при `несовместимых=0` — второй сегмент до сборщика не
доходил вовсе, его не отвергали. А без удержания те же два сегмента уходят на
провод через 130–220 мкс друг за другом (дамп ppp0 того же прогона,
`observe-20260918-142915.pcap`, поток 54628: 1388 байт и следом 146 через
133 мкс). Пока первый сегмент не получил вердикта, ядро остаток не выпускает.

Правило: **кусок, в котором имя уже есть, не удерживается** — план по имени
выбирается прямо сейчас, а ждать нечего и незачем. Сборка остаётся ровно для
того случая, ради которого написана: имя уехало в следующий сегмент. Поле по
этому случаю: «имя уехало во второй сегмент: 0» за все прогоны.

## 3. Исполнитель требовал ЦЕЛУЮ запись

`d2k_plan_apply` при `input tls-sni` сверял объявленную длину записи с пришедшей
и отвергал первый сегмент: «план неприменим к этому пакету» ×2 на зонд.
Приветствие Discord — 1534 байта при MSS 1388, то есть ДВА сегмента всегда.

Теперь вход — запись целиком ИЛИ её начало: объявленные длины сходятся между
собой и пришло не больше объявленного. Действиям плана целой записи не нужно:
имя в сегменте есть, разрезы считаются от него, остаток уйдёт следом сам.

## 4. Контроллер пришпиливал план к длине приветствия

`d2k_arm_plan_measured` выдавал `input %zu %zu %zu` (длина входа и границы
имени) всем плечам, кроме чистой перестановки. Для чистого перекрытия это
неправда: в таком плане нет ни одного числа, снятого с конкретного
приветствия — длина приставки своя, порядок прямой, разрезов нет. Пришпиленная
длина не давала применить план к первому сегменту.

Теперь плечо без приманки и без перестановки объявляет `input tls-sni`
(параметрический вход). Приманка и перестановка пришпиливаются по-прежнему: у
первой длина считается от входа, у второй разрез уезжает в план ЧИСЛОМ.
