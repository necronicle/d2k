Keenetic aarch64, SSH доступен. Перед опытом штатный d2k остановлен, очередь
2000 не привязана, правил NFQUEUE нет. В конфигурации z2k `ENABLED=0`,
процессов nfqws нет. Штатный каталог `/opt/d2k/state/catalog.json` сохранён.

Подняты свежесобранные `d2kd` и `d2kc` в `/tmp`, очередь 537, режим `apply`.
Каталог отдельный, изначально отсутствует. Охват: только IPv4 TCP/443 к
`www.instagram.com`, адрес зафиксирован как `57.144.244.34` через curl
`--resolve`. Прямое обращение **с роутера**, без прокси, TLS 1.3 + HTTP/1.1;
сертификат curl не отключался. PPE не менялся. NFQUEUE — один раз в
POSTROUTING; ответы — INPUT/FORWARD. Ни списки доменов, ни старые планы не
загружались.

## Результат

Исходное обращение без d2k: curl 35, `Connection reset by peer`, HTTP 000.
Первый короткий прогон показал обнаружение и опрос; затем проведён более
длинный с одним инициирующим обращением и 90 сек ожидания.

  собственный зонд. TLS оборван сбросом; кандидат не подтверждён.
- 05:20:23 — очередь исчерпана, цель отдыхает. В последующих сводках
  `планов по целям 0`; подтверждённый каталог не создан.

**Рабочий обход этой цели НЕ найден.** Доказана автономность исследовательского
цикла и отказ записать успех при неудачном TLS, а не доступность Instagram.
Этот опыт не проверяет повторное использование коробки: каталог был пустым.

## Обнаруженный дефект исполнения

За прогон три `sendto: Message too large`, при этом счётчик применений дошёл
до 6. В коде это объясняется порядком: `session.c` добавляет APPLIED, затем
`d2kd.c` вызывает raw send. Ошибка отправки не отзывает APPLIED. Поэтому
«кандидат выбран/посылки построены» сейчас ошибочно смешано с «исполнен».

Точный источник превышения MTU отдельным снимком не устанавливался. Нельзя
списывать локальный EMSGSIZE на свойства DPI. Следующее исправление должно
включать размеры посылок/MTU и явный результат фактического исполнения,
в том числе отложенных пакетов, с привязкой к плану и потоку.
