# Этап 0: три реализации датапата и цена языка

Дата: 2026-09-05. Устройство и условия — те же, что в
`2026-09-05-stage0-datapath.md`: Keenetic на aarch64, ядро 4.9-ndm-5, два ядра
MT7622, офлоад снят в обе стороны для одного клиента.

## Зачем

Первый отчёт заключил, что полная видимость трафика недоступна по цене, и что
язык датапата тут не рычаг, потому что платится за границу ядро/юзерспейс.
**Оба вывода оказались неверны.** Они были сделаны по одной реализации на Go с
библиотекой `mdlayher/netlink`, то есть измеряли её, а не NFQUEUE.

Чтобы разделить цену языка и цену библиотеки, написаны три версии, делающие
буквально одну работу — читать пакет, выставить вердикт до разбора, разобрать
сорок байт заголовка, посчитать:

- `spike/nfqview` — Go поверх `mdlayher/netlink`;
- `spike/nfqview-raw` — Go на голых системных вызовах, без библиотеки;
- `spike/nfqview-c` — C на сыром netlink, без `libnetfilter_queue`;
- `spike/nfqview-rs` — Rust, из зависимостей только `libc` (объявления
  системных вызовов, не рантайм).

## Условия сравнения

Одинаковая нагрузка на каждую конфигурацию: три загрузки по 38 МБ с зеркала
Яндекса, окно 45 с. Колонка «пакетов» печатается намеренно — конфигурации
сравнимы только при равной нагрузке, и она сразу показывает недобор.

Источник нагрузки менялся по ходу: Cloudflare после долгой серии прогонов начал
отдавать 403, два скачивания из трёх возвращали по четыре байта. Конфигурация
получала втрое меньше нагрузки, чем соседняя, а выглядело это как результат.
Оркестратор теперь проверяет код ответа.

| **Go на сисколлах** | 99 467 | **21,4 %** | 5 008 КиБ | **30,4 МБ/с** |

Дропов в ядре нет ни у одной конфигурации.

Проход `go-raw-batch` недостоверен: в этой версии остался таймаут добора пачки
на 200 мс, из-за которого хвост каждой группы застревает. В C он снижен до
20 мс, и там проход групповых вердиктов нормальный. Цифра CPU достоверна.

## Четыре реализации на одном источнике

Отдельный заход, все шесть конфигураций подряд, нагрузка та же:

| реализация | пакетов | CPU (пик) | RSS | проход | бинарник |
|---|---|---|---|---|---|
| **C, попакетно** | 102 960 | **15,0 %** | **224 КиБ** | **32,2 МБ/с** | **69 КБ** |
| C, группой | 103 848 | 10,3 % | 220 КиБ | 24,2 МБ/с | |
| **Rust, попакетно** | 103 676 | **14,9 %** | 864 КиБ | 30,4 МБ/с | 392 КБ |
| Rust, группой | 109 374 | 10,1 % | 868 КиБ | 22,2 МБ/с | |
| Go на сисколлах | 103 537 | 22,0 % | 5 112 КиБ | 29,8 МБ/с | 1 901 КБ |
| Go на сисколлах, группой | 107 995 | 16,3 % | 5 252 КиБ | 16,8 МБ/с | |

**Rust повторяет C по процессору** — 14,9 % против 15,0 % — и отстаёт по проходу
на 6 %. По памяти между ними разрыв вчетверо (864 против 224 КиБ), но обе
величины ничтожны рядом с 5 МБ у Go.

**Go на голых сисколлах дороже Rust и C примерно в полтора раза по процессору**
и в шесть раз по памяти.

**Групповой вердикт — размен, а не улучшение.** У всех трёх он снимает около
трети процессора и стабильно теряет от четверти до сорока процентов прохода.
Это уже не артефакт таймаута (он починен во всех трёх), а плата за задержку
хвоста пачки.

## Что не видно в таблице: сборка под флот

z2k собирается под девять арок, три из них MIPS (`mips`, `mipsle`, `mips64le`),
причём с `GOMIPS=softfloat` — на этих коробках нет сопроцессора.

- **Go** покрывает все девять одной строкой и делает это в проде сегодня.
- **Rust**: в `rustup target list` **нет ни одной MIPS-цели**. Компилятор
  триплеты знает, но готовой стандартной библиотеки для них нет — это третий
  уровень поддержки, то есть nightly и сборка `std` своими руками.
- **C**: `zig cc` покрывает aarch64, arm и x86_64 статикой из коробки, но на
  MIPS musl не даёт вовсе, а gnueabi требует динамической линковки. Нужен
  нормальный кросс-тулчейн Entware/OpenWrt с softfloat — путь известный
  (так собран сам zapret), но это отдельная работа по инфраструктуре сборки.

Для устройства v1 (aarch64) годится любой из трёх. Для флота выбор между C и
Rust упирается не в скорость, а в то, чем их собирать под MIPS.

## Разложение

**Библиотека стоит примерно втрое.** 62,4 % → 21,4 % CPU и 9,1 → 30,4 МБ/с при
переходе на голые системные вызовы. Это аллокации на сообщение и хождение через
рантайм библиотеки, а не свойство языка.

**Язык стоит примерно полтора раза по процессору и девять процентов по
проходу.** 21,4 % → 15,0 % и 30,4 → 33,0 МБ/с. По памяти разрыв больше — 5 МБ
против 224 КиБ, — но на устройстве с 500 МБ это не ограничение.

## Побочные измерения

- **Копирование пакета почти ничего не стоит.** `copylen 0` (только метаданные)
  13,7 % против 16,3 % при полных 1500 байтах. Платим за обмен сообщениями, не
  за байты.
- **Глубина очереди — рычаг.** `qlen 1024` против `8192`: 9,3 % против 15,4 %.
  Совпадает с тем, что поиск вердикта в очереди у ядра линейный по её длине;
  патч на хеш-таблицу подан только в 2025 году, у нас ядро 4.9.
- **GSO ничего не даёт.** С флагом `NFQA_CFG_F_GSO` число пакетов не изменилось
  (108 863 против 112 581) — ядро на этом пути объединённые сегменты не отдаёт.
- **`--queue-balance` не задействует второе ядро на нашей нагрузке.** Две
  очереди получили 110 664 и 598 пакетов: ядро раскладывает по потоку, а
  тяжёлых потоков единицы. Для случая «браузер и несколько соединений»
  параллелизм по очередям бесполезен.
- **Восемь параллельных потоков проходят.** 275 696 пакетов, суммарно
  46,5 МБ/с (372 Мбит/с), около 10 % ядра, дропов нет.

- **QUIC виден в обе стороны.** Нагрузка — настоящие QUIC Initial, которые шлёт
  `z2k-detect quic` с клиента (штатного HTTP/3-клиента на машине нет). За окно
  поймано 162 потока udp/443, у отвеченных зондов `out=1 in=3`: исходящая
  датаграмма и три ответных. Правило `-j PPE` по `--dports 443` и зеркальное по
  `--sports 443` работают так же, как на TCP. Цена — 0,13 % ядра.

  Оговорка: зонд создаёт только рукопожатия. Длинный QUIC-поток (видео) этим
  замером не покрыт и должен вести себя как TCP — уходить в железо после окна
  `connskip`.

## Вывод

Полная видимость трафика **доступна по цене** — вывод 3 первого отчёта неверен
и заменён этим. На C один клиент с полной видимостью в обе стороны стоит 15 %
ядра при 33 МБ/с; восемь параллельных потоков на 372 Мбит/с — около 10 %.

Из этого не следует, что видимость надо включать всем и всегда: бюджет всё
равно конечен, а домашних устройств больше одного. Но она перестаёт быть
недоступной и становится обычным управляемым ресурсом.

## Цена языка, которую не видно в таблице

В примерно 450 строках C за один заход сделаны две ошибки класса «работа с
памятью»:

1. вычитание выровненной длины атрибута из остатка без проверки — при последнем
   атрибуте без хвоста выравнивания счётчик уходил в 2^64 и разбор читал за
   буфером. Сегфолт на первом же пакете, на живом роутере. Сеть не пострадала
   только потому, что правила ставятся с `--queue-bypass`;
2. те же выровненные длины в обходе сообщений.

В обеих версиях на Go ошибок этого класса нет. Единственная ошибка там —
неверное значение константы протокола (`NFQA_VERDICT_HDR` объявлен как 1, в
ядре 2), то есть ошибка данных: она давала EINVAL от ядра и остановку очереди,
но уронить процесс не могла.

Датапат — единственное место продукта, куда чужой пакет из сети попадает в наш
разбор. Полтора раза по процессору покупаются здесь ценой того класса ошибок,
который в этом же замере уже сработал.

## Чего не покрыто

- Длинный QUIC-поток (видео) — только рукопожатия.
- Rust на MIPS не пробовался: цели третьего уровня требуют nightly и сборки
  `std`, и это отдельный опыт.
- C на MIPS не собран: нужен тулчейн Entware/OpenWrt с softfloat.
- `go-raw-batch` требует перезамера после починки таймаута.
- Второе ядро не проверено на нагрузке из многих лёгких потоков, где
  `--queue-balance` мог бы разложиться иначе.
