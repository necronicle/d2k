# Поле 17.09: Дискорд пробит планом d2k, автоматика — нет

Режут не голос, а ПОДКЛЮЧЕНИЕ к нему. Замер с мака при остановленном z2k:

```
gateway.discord.gg    ОБРЫВ
discord.com           ОБРЫВ
cdn.discordapp.com    ОБРЫВ
discord.gg            301 — работает
```

Голосовой поток при этом жив в обоих состояниях (см.
[2026-09-17-voice-field-run.md](2026-09-17-voice-field-run.md)). Звонок без
z2k застревает на «Подключение»: клиент не может дойти до гейтвея по WSS.

## Пробито

Двумя планами, каждый проверен на живой коробке при остановленном z2k:

| план | попыток | итог |
|---|---|---|
| без плана | 8 | все `000` |
| `seqovl payload=1` (один байт перекрытия) | 3 | все `200` |
| фальшивка ×8 с порчей `tcpts` перед приветствием | 5 | все `200`, appconnect ≈ 0,13 с |

Второй — это то же, чем берёт z2k (`fake:...:repeats=8:tcp_ts=-1000` в его
блоке 443), записанное форматом d2k:

```
d2k-plan 1 2
proto tcp tls
payload 1 <ClientHello www.google.com, 681 байт>
poison 1 tcpts
fake payload=1 poison=1 repeats=8 gap_us=0 place=before
order forward
```

Датапат исполнил его без единой ошибки: «план подготовлен 5, ДОИСПОЛНЕН 5,
выпущено 40».

## Измеритель НЕ виноват

Сверено на той же коробке: перенесённый измеритель и ЭТАЛОН `z2k-detect`
дали слово в слово один вердикт и одну стратегию —
`multisplit:pos=1:seqovl=1`. Перенос верен.

Более того, эта стратегия РАБОЧАЯ: планом она даёт 3/3 по 200 (таблица выше).
То есть измеритель нашёл верный ответ.

## Не работает ПОДТВЕРЖДЕНИЕ

Автоматический прогон с контроллером:

```
вердикт: решает содержимое ... кандидатов 1
поставил план 1 из 1 (порт зонда 58285) — испытываю его собственным зондом
план 1: зонд не дошёл до приложения (нет TLS) — беру следующего кандидата
выведенные планы исчерпаны (зондов 1) — цель отдыхает
```

Рабочий план выброшен собственным зондом. Причина одна: **пробный план не
применяется к потоку зонда**.

### Найдено и починено по дороге

1. **Одна метка на две разные задачи.** Правило стенда исключает из очереди
   всё с меткой датапата (`-m mark ! --mark`), а той же меткой ходил зонд
   контроллера. Зонд не доезжал до датапата вовсе. Метки разведены
   (`D2K_CTL_MARK`); после этого приветствие зонда в журнале появилось.

2. **Несимметричная дисциплина доказательств.** Ветка «зонд ПРОШЁЛ» уже
   держала правило: нет доказательства применения — не засчитано. Ветка «зонд
   НЕ дошёл» вела себя обратно: неудача засчитывалась уликой против плана, без
   всякой проверки, применялся ли план к потоку зонда. Асимметрия и выбрасывала
   рабочие планы. Теперь неудача БЕЗ применения — «опыта не было», и кандидат
   переиспытывается один раз (`SCHED_BARE_RETRIES`).

### Что осталось (точно локализовано)

Повтор не помог: план не доехал и со второго раза. Значит это не гонка
«записали команду — зонд ушёл раньше».

Улика: у потока зонда в журнале есть «приветствие discord.com», но НЕТ строки
«план не применён» — в отличие от клиентских потоков, где она есть на каждом.
То есть поток зонда уходит из `handle_tcp` ДРУГОЙ веткой, не через отказ
поиска плана. Кандидаты: `plan_fits_transport`, `fl->plan_done`, повторное
приветствие. Следующий шаг — назвать ветку прямо, а не гадать: счётчик или
запись журнала на каждую из них.

## Оговорки

* Коробка меняется: 13.09 её брал `seqovl-1` и это записано полем; 17.09
  `seqovl-1` по-прежнему берёт, но вердикт называет его «глотает, сервер
  выбрасывает» — формулировка про буфер, не про исход.
* Все замеры — одна линия, один день, цель `discord.com` на одном адресе
  `162.159.128.233`.
* z2k на время каждого замера останавливался и возвращался сразу после.

## Ветка названа: хвост приветствия приходит первым

Поставлен счётчик и запись журнала на каждый исход, и ответ получен числами, а
не рассуждением.

**Шаг 1. Ветка.** У потока зонда в журнале не было строки об отказе плана —
в отличие от клиентских потоков. Заведена запись на исход «составное
приветствие отпущено без сборки», и она появилась ровно на потоке зонда:

```
tcp 88.87.93.11:55245 - 162.159.128.233:443
   план не применён: составное приветствие не собралось — план не применён
   приветствие discord.com
   подозрение: приветствие повторено
```

**Шаг 2. Сколько кусков лежало.** К счётчикам удержания добавлено число
пакетов в слотах, отпущенных по таймауту:

```
составной вход: начато=1 собрано=0 отпущено=1 таймаутов=1 (пакетов в них=1)
```

Один. Значит дело не в разборе — второй кусок до датапата не доходил.

**Шаг 3. Размеры.** В лог выведены объявленная длина записи и пришедшая:

```
объявлено 1534 байт записи, в этом куске 1388
```

Сервер объявил `mss 1400` (видно в захвате на `ppp0`), минус метки времени —
ровно 1388. Приветствие зонда режется на 1388 + 146.

**Шаг 4. Порядок.** Выведен каждый пакет с нагрузкой:

```
пакет 51359->443 seq=3909908605 нагрузка=146     <- ХВОСТ
пакет 51359->443 seq=3909907217 нагрузка=1388    <- голова, ПОСЛЕ
```

Разница 1388: это второй сегмент, пришедший ПЕРВЫМ.

### Дефект

`d2k_session_hold_candidate` признаёт кандидатом только сегмент, стоящий сразу
за SYN (`v.seq != fl->syn_seq + 1` — отказ). Хвост, придя первым, кандидатом
не становится и уходит на провод ГОЛЫМ — прямо в коробку. Затем приходит
голова, заводит удержание и ждёт хвоста, которого уже нет: таймаут, план не
применён, рабочий обход выброшен подтверждением.

Датапат молча предполагал, что куски приветствия приходят по порядку. Сборка
по смещениям у него есть (`capture.c` собирает по seq), а вот НАЧАТЬ удержание
он может только с первого куска.

**Цена.** Вся автоматика подтверждения на этой линии: рабочий план находится,
но не может быть подтверждён и выбрасывается. Ровно это и наблюдалось весь
день на `discord.com`, где обход существует и проверен вручную (200 из 200).

## Причина названа числами: план не успевает дойти до датапата

После починки порядка кусков (ревью P1-1, P1-2) удержание на живой линии
перестало начинаться вовсе. Поставлен счётчик на КАЖДУЮ ветку отказа, и ответ
получен:

```
d2kd: удержание не начато: голова=1 нагрузка=1388 план=нет
d2kd: удержание не начато: голова=0 нагрузка=145  план=нет
```

`план=нет` — и для головы, и для хвоста. Таблица планов датапата в этот момент
ПУСТА: контроллер записал пробный план в управляющий сокет и тут же запустил
зонд, а датапат читает команду своим циклом и не успевает.

Значит цепочка целиком:

1. контроллер ставит план записью в сокет и СРАЗУ запускает зонд;
2. пакеты зонда приходят в датапат раньше команды — плана для цели нет;
3. удержание не начинается, приветствие уходит на провод голым;
4. коробка его режет, зонд не доходит до приложения;
5. рабочий план объявляется негодным и выбрасывается.

Повтор кандидата (уже починенный) это не спасает: он ставит план заново и
снова запускает зонд немедленно — гонка та же.

**Починка не внесена.** Очевидный ход — ждать подтверждения команды перед
испытанием — затрагивает состояние планировщика и в первой же попытке уронил
17 его тестов. Чинить это на скорость нельзя: планировщик несёт весь поиск.
Причина названа и воспроизводима, правка делается отдельным заходом.

Оговорка к самому подтверждению: у датапата события ЛОССИ по контракту, и
ожидание ack требует предела, после которого испытание идёт как есть. В этом
месте порядок однозначен (одна команда, после которой контроллер молчит) — в
отличие от прохода по каталогу, где очередь ожиданий и разъезжалась.

## Гонка установки закрыта, следующая причина названа

**Починено.** Испытание больше не стартует, пока датапат не принял пробный
план: заведено состояние `T_TRIAL_SETTLE`, выход из него — подтверждение
команды `SET_NAME_PROBE` (датапат шлёт его ПОСЛЕ установки плана в таблицу)
либо предел в 50 мс на случай потерянного события.

Привязка к ТИПУ команды обязательна: первая редакция засчитывала любое
подтверждение, включая старое, лежавшее в сокете, и ожидание отпускалось
мгновенно — зонд снова обгонял план. С типом это исправно.

**Проверено живой линией, до и после:**

```
до:    удержание не начато: голова=1 нагрузка=1388 план=нет
после: составной вход: начато=2 ... ; кандидат? голова=1 off=0 план=1
```

То есть план теперь на месте к приходу пакетов зонда — гонка закрыта.

**Следующая причина, названа замером.** Обход всё ещё не подтверждается, и
теперь видно почему. Снимок провода на `ppp0` для потока зонда:

```
seq 1:1389    длина 1388   <- голова, уходит с машины
seq 1389:1535 длина 146    <- хвост, через 0,2 мс
```

Оба сегмента на проводе. Но в датапат попадает ТОЛЬКО голова: она уходит в
удержание и тут же разбирается сессией как приветствие, на потоке взводится
`saw_hello`, и ХВОСТ после этого отсекается первым же условием
`d2k_session_hold_candidate` — раньше всех проверок. Удержание не собирается
никогда и отпускает голову по таймауту.

При этом синтезированный план ТРЕБУЕТ сборки: `d2k_arm_plan_measured` пишет
`input <длина> <смещение имени> <длина имени>` — точные границы снимка, на
котором приём измерен, — а `d2k_plan_stream_input` по этой записи и решает,
что план ложится только на целое приветствие. Ручной план без строки `input`
такой сборки не требовал и потому прошёл (200 из 200).

Правка «хвост при идущем удержании — продолжение» написана и отложена: она
затрагивает разделение «голову когда-то брали» и «удержание идёт прямо
сейчас», и первая редакция ломала соседние случаи. Делается отдельно и с
тестами на каждый.
