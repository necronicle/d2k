# Активный зонд: решение без единого повтора клиента

**Дата:** 2026-09-05, ночь
**Устройство:** Keenetic aarch64, ядро 4.9-ndm-5, z2k остановлен.
**Клиент:** 192.168.1.67, один хост LAN.
**Цель:** linkedin.com (130.211.32.14), блокируется подделанным сбросом.

## Что проверялось

Пассивный поиск ставил кандидата и ждал, пока клиент повторит попытку. На
устройстве, которое не перезапрашивает — телевизор, приставка, часть IoT, —
он не сработал бы вовсе, а срок ожидания задавали бы чужие привычки. Проверка:
клиент ходит ОДИН раз, получает отказ и больше не возвращается.

## Результат

```
    000/0 за 0,096 с            ← единственное обращение клиента, отказ
подозрение по linkedin.com (сброс в ответ на приветствие): начат поиск
по linkedin.com пробую plan-b08307c3 (поиск), попытка 1
по linkedin.com поймана форма приветствия: 322 байт
по linkedin.com стучусь сам: форма клиента -> 130.211.32.14:443
по linkedin.com обмен пошёл (1400 байт, уровень 2): заведена коробка box-486f2788
```

Клиент участвовал ровно один раз. Всё остальное d2k сделал сам: узнал
подозрение, взял форму приветствия у датапата, поставил кандидата, дождался
подтверждения, постучался в цель своим соединением и записал подтверждённое
решение.

Форма приветствия — настоящая, 322 байта от клиентского curl, а не собранная
нами. Это важно: коробка может по-разному относиться к приветствию браузера и
к приветствию нашей библиотеки, и синтетический зонд проверял бы не тот
трафик, что у пользователя (§3.1, §5.5).

## Правила

Зонд идёт С САМОГО РОУТЕРА, а не через него, поэтому транзитных цепочек ему
мало. Понадобились ещё две:

```
mangle OUTPUT  -p tcp --dport 443 -m mark ! --mark N -m connbytes 0:8 ...  → NFQUEUE
mangle INPUT   -p tcp --sport 443                    -m connbytes 0:8 ...  → NFQUEUE
```

Без них план к зонду не применился бы, и зонд мерил бы линию БЕЗ обхода,
считая, что мерит с обходом. Это была бы не ошибка измерения, а измерение
не того.

## Скорость

Из прошлого замера: от подозрения до применённого плана — 77 мс. Зонд
добавляет один сетевой круг до цели. Ожидание повторов клиента исчезло из
формулы совсем.

## Чего этот прогон не доказывает

- **Путь результата зонда не проверен на устройстве.** Подтверждение пришло
  по пассивному пути: собственный трафик зонда идёт через датапат и порождает
  те же наблюдения, а датапат видит байты раньше, чем Go возвращается из
  чтения. Оба пути верны, но в поле сработал первый.
- Один цель, одна линия, один прогон.
- Зонд ходит с адреса роутера, а не клиента. Для NAT-линии это другой поток с
  точки зрения коробки, и §5.5 требует «сопоставимого выхода» — здесь он
  сопоставим по маршруту и по форме приветствия, но не по адресу источника.
  Что это меняет, не измерено.
