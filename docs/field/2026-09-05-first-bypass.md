# Первый подобранный обход на живой линии

**Дата:** 2026-09-05, вечер
**Устройство:** Keenetic aarch64, ядро 4.9-ndm-5, WAN `ppp0`, внешний адрес 88.87.93.11.
**Линия:** z2k остановлен. Никакого другого обхода не работало.
**Клиент:** 192.168.1.67, один хост LAN.
**Сужение:** правила только на пару «этот клиент — эта цель». §2.6: на роутере
живут чужие устройства, и десинк всего 443-го порта был бы не экспериментом, а
аварией.

## Критерий, заданный ДО опыта

Успех: код 200 и больше 1000 байт против базовой линии (код 000, 0 байт).

Критерий оказался слишком узким, и документ предупреждал ровно об этом: §4.2
говорит, что «короткий корректный ответ не является неудачей только из-за
размера». На instagram.com рукопожатие прошло и сервер вернул 301 с пустым
телом — это успех уровня 3–4 по §4.2, а не провал, хотя байт ноль. Порог в
байтах годится как условие конкретного опыта и не годится как определение
успеха. Записано здесь, а не переписано задним числом.

## Что было измерено на linkedin.com

Четыре настройки, одна цель, один адрес, подряд.

| Настройка | Результат |
|---|---|
| без ничего | код 000, 0 байт, отказ мгновенный (0,05 с) |
| только фальшивка | код 000, 0 байт |
| только защита | код 000, 0 байт, отказ через таймаут (12 с) |
| **фальшивка и защита** | **код 200, 21 150 байт, 0,17 с — трижды подряд** |

Ни одна половина по отдельности не работает.

### Что показал снимок трафика

Без защиты, в момент отказа:

```
21:03:00.561921  наша фальшивка   ttl 3,   id 1,      сумма неверна, 119 байт
21:03:00.561938  приветствие      ttl 63,  322 байта
21:03:00.562259  СБРОС            ttl 127, id 54321,  tos 0x88, без опций
21:03:00.603440  сервер: ack 323  ttl 124, tos 0x70,  с метками времени
21:03:00.605902  наш клиент: RST  — принял подделку
21:03:00.606710  сервер: 1400 байт
21:03:00.606728  сервер: 1400 байт
21:03:00.606741  сервер: 1400 байт
21:03:00.606751  сервер: 187 байт
```

**Настоящий сервер ответил 4388 байтами ServerHello.** Соединение убил
клиент, приняв подделанный сброс за настоящий.

Подделка отличается от пакетов сервера по четырём признакам сразу: TTL 127
против 124, идентификатор IP постоянный 54321 против последовательного, ToS
0x88 против 0x70, опций нет против меток времени. И приходит через 0,3 мс,
тогда как настоящий обмен с этим сервером идёт с RTT 41 мс.

Наша фальшивка при этом ушла на провод правильно: адрес источника 88.87.93.11,
то есть ядро провело её через NAT так же, как настоящий пакет, и она
опередила настоящее приветствие на 17 мкс.

С защитой, но без фальшивки:

```
приветствие → подделанный сброс (снят) → приветствие ещё раз → тот же сброс
```

Девять повторов приветствия, девять одинаковых подделок (тот же seq, тот же
идентификатор, та же контрольная сумма — буквально один и тот же пакет), и
**сервер не ответил ни разу**. То есть фальшивка не просто отвлекает: без неё
приветствие до сервера не доходит.

## Обобщение на другие цели

Тот же план, разные цели. Соединение закреплено на конкретном адресе через
`curl --resolve`: §5.5 требует одного фактического IP на сравниваемую серию, и
первая попытка без закрепления измерила пустоту — DNS отдавал один адрес,
а правило стояло на другом, план не применялся ни разу.

| Цель | Базовая линия | С планом | Снято подделок |
|---|---|---|---|
| linkedin.com | 000, 0 байт, мгновенно | **200, 21 150 байт** | 3 |
| discord.com | 000, 0 байт, таймаут 8 с | **200, 170 036 байт** | **0** |
| instagram.com | 000, 0 байт | **301** (рукопожатие прошло) | 2 |
| www.torproject.org | 000, 0 байт | 000, 0 байт | 2 |

Три цели из четырёх. По §2.3 про четвёртую не сохраняется ничего — ни как
«непробиваемая», ни как отметка на цели. Она просто не записана.

**Discord важнее прочих:** подделок снято НОЛЬ. Его блокировка — молчание, а
не сброс, и справилась с ней одна фальшивка. То есть за одним планом стоят
два разных наблюдаемых поведения, и приписывать им одну коробку нельзя
(§2.4, §3.2). Различие видно и в базовой линии: мгновенный отказ у linkedin
против восьмисекундного таймаута у discord.

## Использованный план

```
d2k-plan 1 2
proto tcp tls
payload 1 <целое правдоподобное приветствие с именем disk.rzd.ru>
poison 1 ttl=3 badsum
fake payload=1 poison=1 repeats=2 gap_us=78000 place=before
order forward
guard rst_alien
```

Первые пять строк — плечо донора, записанное форматом d2k. Последняя —
собственная операция, появившаяся из этого замера.

## Чем защита отличается от той, что была у донора

У донора RST-фильтр «никому реально не помог», и причины записаны: правило
`-m u32` по идентификатору IP 0..15 снимало НАСТОЯЩИЕ сбросы Linux-серверов
(они ходят с id 0) и не ловило подделку с id 54321 вовсе; второй механизм,
`--rst-filter` в движке, снимал сброс раньше собственного детектора и ослеплял
ротацию.

Здесь ориентир не константа, а **первый пакет с той стороны в этом же
соединении** — обычно SYN-ACK. Он не может разойтись с потоком, потому что взят
из него. Подозрение отмечается ДО снятия, поэтому обучение не слепнет.

## Чего этот опыт не доказывает

- Устройства коробки. §2.4: успех воздействия подтверждает его полезность в
  измеренном контексте и не устанавливает внутреннее устройство DPI.
- Переносимости на другие линии и провайдеров. Измерена одна линия.
- Устойчивости во времени. Три попытки подряд — не сутки.
- Безопасности защиты на широком трафике. Правило стояло на одной паре
  адресов; поведение при снятии сбросов на всём 443-м порту не измерялось, и
  до такого замера включать защиту широко нельзя.
- Что `ttl=3` — верное число. Оно из плеча донора, а не из измерения
  расстояния до коробки на этой линии. Подделка приходит с TTL 127, что при
  начальном 128 означает один хоп, — но это оценка, а не замер.
