# Повторное ревью и границы доказательства — 12.09.2026

База ревью: `f8149b4`. Это продолжение MVP, не новая архитектура и не
приёмка полноценной замены z2k. Изменения этой вертикали пока в рабочем дереве.

## Оценка продолжения

Направление сохранено. Собственный `d2kd` исполняет Plan; `d2kc` начинает с
готовых планов совместимых коробок, затем исследует и синтезирует новые.
Измеритель «Стратегии по доменам» остаётся основой исследовательской части.
Никаких поставляемых доменных списков, nfqws или исполнения Zapret не добавлено.
NFQUEUE — интерфейс ядра Linux, а не зависимость от nfqws; его использование
не противоречит собственному движку.

Полезные изменения коллеги: автономные испытания кандидатов, ID применённого
плана в событии, `shape`/`verified_by`, стенные даты, проверка и восстановление
firewall. Их сохраняем. Но объявление «без ложного успеха» было преждевременным.

## Исправлено в этой вертикали

1. Последующий внешний TLS type 23 больше **не повышает** запись до уровня 5
   и не переписывает `verified_by=probe` в `client`. Это наблюдение даже после
   успешного собственного зонда: второй клиент мог остановиться на handshake.
2. Ранние APPLIED сохраняются ограниченным набором полных ключей потока.
   Совпадение одного клиентского порта недостаточно: другой LAN-клиент может
   использовать такой же порт. Поздний результат зонда сверяет оба IP, оба
   порта, транспорт; событие дополнительно проверено по ID кандидата.
   Пустой ID не принимается. Переполнение набора означает потерю улики, не успех.
3. Транскрипт TLS, входной и выходной буферы больше не общие `static`:
   они принадлежат сессии. Буферы объёмного запроса также локальны вызову.
   Иначе параллельные зонды портили чужие данные. Усечённый объёмный запрос
   не отправляется с длиной за пределами буфера.
4. HTTP собирается через границы TLS-записей до завершения заголовков;
   проверяется полная status line. Промежуточные 1xx пропускаются до конечного
   ответа, 101 без запроса upgrade не принимается. Оборванный `HTTP/1.1 200`,
   четырёхзначный код и неверная версия не подтверждают попытку.
   Сборка ограничена 8 КиБ и общим временем ожидания заголовков.
   Управляющие символы в Host отвергаются до обращения в сеть.
5. Полевой скрипт не ставит второй NFQUEUE в OUTPUT поверх POSTROUTING,
   ограничивает PPE той же целью/клиентом, останавливает временный контроллер
   и tcpdump при уборке, сохраняет журнал контроллера и временный каталог.
   Заимствованное SSH-соединение больше не закрывает.

Регрессии: чужой IP с совпавшим портом до завершения зонда; своё событие после
чужого; отсутствующий ID; пассивный TLS после probe не повышает достоверность;
фрагментированный/оборванный/промежуточный HTTP; 4 параллельных TLS-зонда.

## Что по-прежнему НЕ доказано

- **Исполнение всех посылок плана.** `session.c` журналирует APPLIED при
  построении результата, ДО `d2k_raw_send` в `d2kd.c`. Ошибка отправки или
  отложенной очереди не отзывает событие. На узкой живой пробе получено
  `sendto: Message too large` одновременно с ростом «план применён».
  Таким образом, даже правильные ID и ключ потока ещё не подтверждают
  доставку всех воздействий ядру. Нужен отдельный результат исполнения
  (включая отложенные посылки); локальный отказ нельзя записывать как
  свойство коробки. В этой вертикали контракт события не переделан.
- **Доступность настоящего сайта.** Минимальный TLS-клиент не проверяет
  цепочку сертификатов, hostname, CertificateVerify и Finished сервера.
  Получение HTTP внутри такой сессии может быть ответом посредника.
  Статус 403 или 451 — не доказательство отсутствия блокировки; даже 200
  может быть заглушкой. Тело и требуемый объём также не проверены.
  `D2K_VER_APPLICATION` сейчас означает только полученные HTTP-заголовки.
- **Переносимость успеха на клиента.** `shape` — грубая классификация, не
  отпечаток браузера. Метаданные каталога не равны ограничению применения:
  SET_NAME не доставляет датапату полноценный контекст. Ноль в старом файле
  остаётся wildcard, но неизвестный контекст не доказан для всех клиентов.
- **Единственная определённая коробка.** Совпадение пассивных признаков и
  успех общего плана дают гипотезу совместимости. Активные свойства ещё не
  входят в устойчивую модель; дедупликация общего плана теряет альтернативных
  владельцев. Не называть полученный box ID физически установленным DPI.
- **Старые знания.** Записи прежнего критерия, включая level 5, не стали
  достовернее после исправлений. Их не удаляли и массово не переписывали.
  Нужна версия доказательства и явная перепроверка. Обновление существующей
  привязки может сохранить старый высокий level при новом `verified_by=probe`;
  это также требуется исправить в модели хранения свидетельств.
- QUIC end-to-end, TLS 1.2 собственным зондом, STUN, IPv6, безымянные цели,
  поздние обрывы, полный охват портов и общий бюджет всех сетевых проб не готовы.
- Фиксированный контроль диагностики и гарантированное снятие временного
  плана при потере управляющей связи остаются открытыми.

## Следующая вертикаль — не косметика панели

Уточнение после замечания пользователя: сверка выявила также утрату части
поиска и изменение воздействий донора. Порядок восстановления функционала и
критерии эквивалентности — в [решении 0007](0007-donor-parity.md). Работы ниже
нужны для достоверности, но не заменяют сохранение поисковых возможностей.

1. Довести факт исполнения от raw send/отложенной очереди до контроллера:
   MTU/EMSGSIZE и частичное исполнение не дают положительного свидетельства.
   Затем разделить в данных «HTTP получен», «сервер аутентифицирован», «объём
   проверен», «сервис доступен» и «проверено клиентом». Хранить версию прибора
   и контекст свидетельства; не повышать достоверность по одному счётчику.
2. Для подтверждения настоящего сервера подключить проверенный TLS-стек с
   trust store и hostname verification. Собственный пакетный движок не требует
   самостоятельно реализовывать X.509. Диагностический TLS с подставным SNI
   оставить отдельно, не выдавать его результат за аутентификацию цели.
3. Провести контекст через каталог → управляющий протокол → выбор плана
   датапатом; неизвестный клиент должен сначала проверить кандидата, а не
   наследовать успех зонда. Требуются тесты двух форм к одному имени.
4. После этого — повторное использование коробки на второй цели без нового
   исследования, затем QUIC и остальные классы. Полевые тесты — с пустым
   временным каталогом и узким охватом, эксплуатационный каталог сохранять.

Основание разбора HTTP: [RFC 9112 §4](https://www.rfc-editor.org/rfc/rfc9112.html#section-4),
[RFC 9110 §15.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.2).
Итоги конкретных проверок и полевого прогона фиксируются отдельно в
`docs/field/2026-09-12-proof-review.md`.
